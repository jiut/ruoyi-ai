## 1. 背景说明

### 1.1 业务全貌分析
设计师生态管理系统是一个复杂的多角色平台，涉及用户、设计师、企业、院校等多个实体，以及用户绑定、角色选择、档案管理等多种业务场景。基于完整业务分析，确定需要实施全面的逻辑删除机制。

### 1.2 业务特点
- **多身份绑定**: 用户可同时拥有设计师、企业员工、院校学生等多重身份
- **渐进式注册**: 从基础注册到完整档案的渐进式信息收集
- **数据关联性强**: 设计师档案包含基础信息、工作经历、教育背景、作品展示、获奖记录等多维度数据
- **历史价值高**: 设计师职业发展轨迹具有重要的历史参考价值
- **法律合规要求**: 涉及学历认证、工作经历证明等法律文件，需要长期保存
- **业务连续性**: 支持暂停使用、重新激活等业务场景

## 2. 用户生命周期删除策略

### 2.1 用户生命周期阶段

#### 2.1.1 注册阶段
- **基础注册**: 用户创建系统账户，此时可直接物理删除
- **角色选择**: 用户选择角色类型，产生角色绑定关系
- **身份注册**: 完成具体身份信息填写，创建实体档案

#### 2.1.2 使用阶段
- **信息补充**: 用户逐步完善档案信息
- **正常使用**: 用户正常使用系统功能
- **暂停使用**: 用户暂时停用账户，但保留数据

#### 2.1.3 注销阶段
- **软删除**: 用户主动注销，数据标记删除但可恢复
- **硬删除**: 管理员删除，数据进入回收站
- **物理删除**: 超过保留期限，数据彻底清理

### 2.2 分阶段删除策略

#### 2.2.1 即时删除场景
- 用户仅完成基础注册，未产生业务数据
- 测试数据和垃圾数据清理
- 系统维护需要的临时数据清理

#### 2.2.2 逻辑删除场景
- 用户已完成身份注册，产生档案数据
- 用户有正在进行的业务流程（申请、招聘等）
- 涉及多方业务关系的数据

#### 2.2.3 渐进式删除策略
```
用户删除请求 → 软删除（30天） → 硬删除（90天） → 物理删除（365天）
```

## 3. 多身份绑定删除机制

### 3.1 身份绑定关系分析

#### 3.1.1 单身份用户
- **设计师身份**: 独立设计师，只有设计师档案
- **企业身份**: 企业管理员，只有企业档案
- **院校身份**: 院校管理员，只有院校档案

#### 3.1.2 多身份用户
- **设计师 + 企业员工**: 在校学生同时是企业实习生
- **设计师 + 院校学生**: 在校学生设计师
- **设计师 + 企业 + 院校**: 复合身份用户

### 3.2 多身份删除规则

#### 3.2.1 部分身份删除
- **删除设计师身份**: 保留企业、院校身份
- **删除企业身份**: 保留设计师、院校身份
- **删除院校身份**: 保留设计师、企业身份

#### 3.2.2 完全身份删除
- **删除所有身份**: 用户账户彻底注销
- **级联删除处理**: 按照优先级处理关联数据
- **数据归属处理**: 多身份共享数据的归属处理

### 3.3 身份删除优先级
```
1. 设计师身份 (最高优先级，影响作品、经历等核心数据)
2. 企业身份 (中等优先级，影响招聘、岗位等)
3. 院校身份 (中等优先级，影响学生、统计等)
4. 用户绑定关系 (最低优先级，最后处理)
```

## 4. 逻辑删除标准

### 4.1 核心原则

#### 4.1.1 数据保护原则
- **永不丢失**: 所有业务数据只能标记删除，不能物理删除
- **可恢复性**: 提供完整的数据恢复机制
- **审计可追溯**: 保留完整的操作记录和时间戳

#### 4.1.2 业务连续性原则
- **渐进式删除**: 支持软删除、硬删除的分级处理
- **关联数据保护**: 主数据删除时，关联数据同步标记删除
- **权限分离**: 不同角色对已删除数据有不同的访问权限
- **多身份兼容**: 支持多身份用户的复杂删除场景

#### 4.1.3 性能优化原则
- **查询效率**: 通过索引优化保证逻辑删除不影响查询性能
- **存储成本**: 合理设计数据归档策略，平衡存储成本和数据价值
- **系统稳定性**: 逻辑删除操作应该是原子性的，避免数据不一致

### 4.2 分级删除机制

#### 4.2.1 软删除（用户自主删除）
- **状态标记**: `del_flag = '0'` → `del_flag = '1'`
- **保留期限**: 30天内可自主恢复
- **访问权限**: 用户自己可见，其他用户不可见
- **恢复机制**: 用户可通过个人中心恢复

#### 4.2.2 硬删除（管理员删除）
- **状态标记**: `del_flag = '1'` → `del_flag = '2'`
- **保留期限**: 90天内可管理员恢复
- **访问权限**: 仅管理员可见
- **恢复机制**: 需要管理员权限恢复

#### 4.2.3 物理删除（系统清理）
- **状态标记**: `del_flag = '2'` → 物理删除
- **保留期限**: 365天后自动清理
- **访问权限**: 完全不可见
- **恢复机制**: 无法恢复，需要数据备份

### 4.3 技术标准

#### 4.3.1 数据库字段标准
所有涉及逻辑删除的表必须包含以下字段：
```sql
-- 逻辑删除字段（系统控制，用户不可见）
`del_flag` char(1) DEFAULT '0' COMMENT '删除标志（0正常 1软删除 2硬删除）',
`del_time` datetime DEFAULT NULL COMMENT '删除时间',
`del_by` bigint DEFAULT NULL COMMENT '删除人ID',

-- 业务状态字段（业务控制，用户可见）
`status` char(1) DEFAULT '0' COMMENT '状态（0正常 1停用）'
```

#### 4.3.2 实体类配置标准
```java
@Data
@EqualsAndHashCode(callSuper = true)
@TableName("table_name")
public class EntityName extends BaseEntity {
    
    /**
     * 状态（0正常 1停用）
     * 业务状态控制，用户可见，管理员可操作
     */
    @Pattern(regexp = "^[01]$", message = "状态值必须为0或1")
    @Schema(description = "状态", example = "0", allowableValues = {"0", "1"})
    private String status;
    
    /**
     * 删除标志（0正常 1软删除 2硬删除）
     * 系统控制，用户不可见，影响数据查询
     */
    @TableLogic(value = "0", delval = "1")
    @JsonIgnore
    @Schema(description = "删除标志", hidden = true)
    private String delFlag;
    
    /**
     * 删除时间
     */
    @JsonIgnore
    @Schema(description = "删除时间", hidden = true)
    private Date delTime;
    
    /**
     * 删除人ID
     */
    @JsonIgnore
    @Schema(description = "删除人ID", hidden = true)
    private Long delBy;
}
```

#### 4.3.3 status与delFlag的区别与配合

**字段对比表**：

| 字段 | 用途 | 可见性 | 操作方式 | 值域 | 自动处理 |
|------|------|--------|----------|------|----------|
| `status` | 业务状态控制 | 用户可见 | 管理员手动操作 | 0正常/1停用 | 需显式查询条件 |
| `delFlag` | 数据删除控制 | 用户不可见 | 系统自动设置 | 0正常/1软删除/2硬删除 | MyBatis-Plus自动过滤 |

**使用场景**：
- **status = '1'（停用）**: 业务暂停，数据保留，用户不可访问，管理员可查看
- **delFlag = '1'（软删除）**: 数据标记删除，一般查询不可见，可恢复
- **delFlag = '2'（硬删除）**: 数据待清理，仅管理员可见，用于回收站
- **物理删除**: 数据彻底清除，不可恢复

**查询优先级**：
```
1. delFlag过滤（MyBatis-Plus自动处理）
2. status过滤（业务查询显式添加）
3. 其他业务条件过滤
```

#### 4.3.4 索引优化标准
为保证查询性能，必须为`del_flag`和`status`字段创建复合索引：
```sql
-- 示例：为设计师表创建复合索引
CREATE INDEX `idx_designer_del_flag_status` ON `des_designer`(`del_flag`, `status`);
CREATE INDEX `idx_designer_del_time` ON `des_designer`(`del_time`);
CREATE INDEX `idx_designer_status_create_time` ON `des_designer`(`status`, `create_time`);
```

### 5.3 删除类型说明

#### 5.3.1 分级删除
- 支持软删除（用户）→硬删除（管理员）→物理删除（系统）三级处理
- 适用于核心业务实体表：设计师、企业、院校、用户绑定
- 需要完整的恢复机制和权限控制

#### 5.3.2 级联删除（逻辑）
- 当主表记录删除时，关联表记录同步标记删除
- 适用于从属关系明确的子表
- 删除级别与主表保持一致
- **替换当前危险的数据库级联删除**

#### 5.3.3 物理删除
- 直接从数据库中删除记录
- 适用于临时数据和行为数据：收藏、访问记录等
- 不涉及核心业务连续性

    @Override
    @Transactional(rollbackFor = Exception.class)
    public boolean deleteDesigner(Long designerId) {
        // 1. 验证设计师是否存在
        Designer designer = this.getById(designerId);
        if (designer == null) {
            throw new ServiceException("设计师不存在");
        }
        
        // 2. 检查权限
        if (!hasPermissionToDelete(designerId)) {
            throw new ServiceException("无权限删除此设计师");
        }
        
        // 3. 逻辑删除设计师主记录
        boolean result = this.removeById(designerId);
        
        // 4. 同步删除关联数据
        if (result) {
            // 删除工作经历
            workExperienceService.deleteByDesignerId(designerId);
            // 删除教育背景
            educationService.deleteByDesignerId(designerId);
            // 删除作品
            workService.deleteByDesignerId(designerId);
            // 删除获奖记录
            awardService.deleteByDesignerId(designerId);
        }
        
        return result;
    }
    
    /**
     * 恢复已删除的设计师
     * @param designerId 设计师ID
     * @return 恢复结果
     */
    @Override
    @Transactional(rollbackFor = Exception.class)
    public boolean restoreDesigner(Long designerId) {
        // 1. 查询已删除的设计师（需要包含已删除数据）
        Designer designer = this.getById(designerId, true);
        if (designer == null) {
            throw new ServiceException("设计师不存在");
        }
        
        // 2. 检查权限（只有管理员可以恢复）
        if (!LoginHelper.isSuperAdmin()) {
            throw new ServiceException("无权限恢复设计师数据");
        }
        
        // 3. 恢复设计师主记录
        designer.setDelFlag("0");
        boolean result = this.updateById(designer);
        
        // 4. 同步恢复关联数据
        if (result) {
            workExperienceService.restoreByDesignerId(designerId);
            educationService.restoreByDesignerId(designerId);
            workService.restoreByDesignerId(designerId);
            awardService.restoreByDesignerId(designerId);
        }
        
        return result;
    }
}

/**
 * 更新设计师状态（启用/停用）
 * @param designerId 设计师ID
 * @param status 状态（0正常 1停用）
 * @return 更新结果
 */
@Override
@Transactional(rollbackFor = Exception.class)
public boolean updateDesignerStatus(Long designerId, String status) {
    // 1. 验证设计师是否存在
    Designer designer = this.getById(designerId);
    if (designer == null) {
        throw new ServiceException("设计师不存在");
    }
    
    // 2. 检查权限
    if (!hasPermissionToUpdateStatus(designerId)) {
        throw new ServiceException("无权限修改此设计师状态");
    }
    
    // 3. 验证状态值
    if (!"0".equals(status) && !"1".equals(status)) {
        throw new ServiceException("状态值无效");
    }
    
    // 4. 更新状态
    LambdaUpdateWrapper<Designer> wrapper = new LambdaUpdateWrapper<>();
    wrapper.eq(Designer::getDesignerId, designerId)
           .set(Designer::getStatus, status);
    
    boolean result = this.update(wrapper);
    
    // 5. 记录状态变更日志
    if (result) {
        String operation = "0".equals(status) ? "启用" : "停用";
        log.info("设计师状态更新成功 - 设计师ID: {}, 操作: {}, 操作人: {}", 
                designerId, operation, LoginHelper.getUserId());
    }
    
    return result;
}

/**
 * 批量更新设计师状态
 * @param designerIds 设计师ID列表
 * @param status 状态（0正常 1停用）
 * @return 更新结果
 */
@Override
@Transactional(rollbackFor = Exception.class)
public boolean batchUpdateDesignerStatus(List<Long> designerIds, String status) {
    if (designerIds == null || designerIds.isEmpty()) {
        return false;
    }
    
    // 验证权限
    for (Long designerId : designerIds) {
        if (!hasPermissionToUpdateStatus(designerId)) {
            throw new ServiceException("无权限修改设计师ID " + designerId + " 的状态");
        }
    }
    
    // 批量更新状态
    LambdaUpdateWrapper<Designer> wrapper = new LambdaUpdateWrapper<>();
    wrapper.in(Designer::getDesignerId, designerIds)
           .set(Designer::getStatus, status);
    
    return this.update(wrapper);
}

/**
 * 检查状态更新权限
 */
private boolean hasPermissionToUpdateStatus(Long designerId) {
    // 超级管理员无限制
    if (LoginHelper.isSuperAdmin()) {
        return true;
    }
    
    // 院校管理员只能修改本校设计师状态
    if (permissionUtils.isSchool()) {
        Designer designer = this.getById(designerId);
        if (designer == null) return false;
        
        Long schoolId = permissionUtils.getCurrentSchoolId();
        return designer.getSchoolId() != null && designer.getSchoolId().equals(schoolId);
    }
    
    // 企业管理员只能修改本企业设计师状态
    if (permissionUtils.isEnterprise()) {
        Designer designer = this.getById(designerId);
        if (designer == null) return false;
        
        Long enterpriseId = permissionUtils.getCurrentEnterpriseId();
        return designer.getEnterpriseId() != null && designer.getEnterpriseId().equals(enterpriseId);
    }
    
    // 设计师不能修改状态
    return false;
}

 * 检查删除权限
 */

    // 超级管理员无限制
    if (LoginHelper.isSuperAdmin()) {
        return true;
    }

        return currentDesignerId != null && currentDesignerId.equals(designerId);

        return designer.getSchoolId() != null && designer.getSchoolId().equals(schoolId);
    }
    
    // 其他角色无删除权限
    return false;

## 10. 用户绑定关系修复方案

### 10.1 问题分析

#### 10.1.1 问题描述
在当前实现中，删除设计师后，用户绑定信息仍然存在，导致用户重新绑定新设计师时返回错误：
```json
{
    "code": 500,
    "msg": "用户已绑定设计师身份",
    "data": null
}
```

#### 10.1.2 根本原因
1. **删除时未处理绑定关系**：在 `DesignerServiceImpl.cascadeDeleteRelatedData()` 方法中，没有处理用户绑定关系
2. **检查逻辑冲突**：`isUserBoundToEntityType()` 只查询 `binding_status = '1'` 的有效绑定记录
3. **状态冲突**：删除设计师后，用户绑定记录仍然存在且状态为有效，导致重新绑定失败

#### 10.1.3 影响范围
- **设计师身份重新绑定失败**：用户无法重新注册设计师身份
- **数据一致性问题**：绑定表与实体表状态不一致
- **用户体验影响**：用户困惑，无法理解为什么绑定失败

### 10.2 解决方案

#### 10.2.1 核心思路
- **删除时同步处理**：删除设计师时，同步将对应的用户绑定状态设置为解绑状态
- **恢复时同步处理**：恢复设计师时，同步恢复用户绑定关系
- **数据修复**：修复现有的孤立绑定数据

#### 10.2.2 技术实现

**新增接口方法**：
```java
// IUserBindingService.java
/**
 * 根据实体类型和实体ID删除绑定关系（设置为解绑状态）
 */
Boolean unbindByEntityTypeAndId(UserEntityType entityType, Long entityId);

/**
 * 批量根据实体类型和实体ID删除绑定关系
 */
Boolean batchUnbindByEntityTypeAndIds(UserEntityType entityType, List<Long> entityIds);

/**
 * 批量根据实体类型和实体ID恢复绑定关系
 */
Boolean batchRestoreByEntityTypeAndIds(UserEntityType entityType, List<Long> entityIds);
```

**实现逻辑**：
```java
// UserBindingServiceImpl.java
@Override
public Boolean batchUnbindByEntityTypeAndIds(UserEntityType entityType, List<Long> entityIds) {
    if (entityIds == null || entityIds.isEmpty()) {
        return true;
    }
    
    // 批量更新绑定状态为解绑
    LambdaUpdateWrapper<UserBinding> wrapper = new LambdaUpdateWrapper<>();
    wrapper.eq(UserBinding::getEntityType, entityType.getCode())
            .in(UserBinding::getEntityId, entityIds)
            .eq(UserBinding::getBindingStatus, "1")  // 只更新当前为绑定状态的记录
            .set(UserBinding::getBindingStatus, "0"); // 设置为解绑状态
    
    return update(wrapper);
}
```

## 附录：status与delFlag字段配合使用示例

### A.1 各种状态组合的业务含义

| status | delFlag | 状态描述 | 查询可见性 | 业务含义 | 操作建议 |
|--------|---------|----------|------------|----------|----------|
| 0 | 0 | 正常启用 | ✅ 公开可见 | 设计师正常使用系统 | 无需操作 |
| 1 | 0 | 正常停用 | ❌ 公开不可见<br/>✅ 管理员可见 | 设计师账户被暂停，可恢复 | 管理员可启用 |
| 0 | 1 | 启用但软删除 | ❌ 一般查询不可见<br/>✅ 回收站可见 | 设计师删除账户，可恢复 | 用户/管理员可恢复 |
| 1 | 1 | 停用且软删除 | ❌ 一般查询不可见<br/>✅ 回收站可见 | 设计师被停用后又删除账户 | 管理员可恢复 |
| 0/1 | 2 | 任意状态硬删除 | ❌ 一般查询不可见<br/>✅ 管理员回收站可见 | 管理员删除，等待清理 | 仅管理员可恢复 |

### A.2 查询API行为示例

```java
// 1. 公开查询（如企业招聘查看设计师）
// 只返回：status=0 AND delFlag=0 的记录
designerService.selectPublicDesignerList(designer);

// 2. 管理员查询所有正常数据（包括停用）
// 返回：delFlag=0 的记录（status可以是0或1）
designerService.selectDesignerListIncludeDisabled(designer);

// 3. 管理员查询回收站
// 返回：delFlag=1或2 的记录（不考虑status）
designerService.selectDesignerListIncludeDeleted(designer);

// 4. 管理员查询停用列表
// 返回：status=1 AND delFlag=0 的记录
designerService.selectDesignerListIncludeDisabled(designerWithStatus1);
```

### A.3 操作优先级建议

1. **用户正常使用**: status=0, delFlag=0
2. **临时暂停服务**: 修改status=1（停用），保持delFlag=0
3. **用户删除账户**: 修改delFlag=1（软删除），保持status值不变
4. **管理员强制删除**: 修改delFlag=2（硬删除）
5. **系统自动清理**: 物理删除delFlag=2且超期的记录
